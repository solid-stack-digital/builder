# Solid Stack Builder V2 — Comprehensive Test Conditions

## Purpose

This directory is a specification-driven conformance suite for the future Solid Stack Builder V2 implementation.

It is intentionally written **before implementation**. The expected behavior is defined by the Builder V2 configuration architecture, not by the behavior of the current Builder code. An implementation is conformant only when these scenarios pass without weakening the documented invariants.

The suite contains **384 scenarios across 11 focused test catalogs**.

## Normative source hierarchy

Use the finalized V2 documentation as the oracle:

1. `SPECS_V2.md` — cross-file architecture and normative invariants.
2. `BUILD_JSON_DOCS.md` — complete `build.json` field contract.
3. `MESH_JSON_DOCS.md` — complete `mesh.json` field contract.

When a test fixture intentionally contains invalid configuration, the expected behavior is a **compile/configuration-time failure** unless the scenario explicitly states that runtime behavior is required to prove the invariant. Do not make an invalid case pass by silently coercing, dropping, translating, remapping, or weakening configuration.

## Required test layers

Implement the scenarios at the lowest layer capable of proving the behavior, then retain selected higher-layer tests as integration/regression coverage:

- **Schema/config tests** — JSON shape, exact field types, identifier regexes, required/forbidden/legacy fields, path boundaries.
- **Compiler tests** — stage merge, endpoint/reference resolution, provider substitution, publication, namespacing, lifecycle graph generation, generated Compose, deterministic port allocation.
- **Docker/Compose integration tests** — actual health transitions, service DNS/network reachability, module-wide environment propagation, host publication, resource isolation, and atomic dependency materialization.
- **CLI orchestration tests** — command-to-stage mapping, unit→E2E sequencing, fail-fast behavior, runner exit code, cleanup, and end-to-end black-box execution.

A compile-only golden test is insufficient when the V2 requirement is explicitly behavioral (for example, proving that an unhealthy dependency actually blocks an app).

## Fixture design rules

Keep reusable fixtures under a test-fixture root rather than creating bespoke application logic in every test. The fixture library should include:

- a tiny HTTP app capable of exposing multiple ports, reporting runtime env, delaying readiness, and writing start/health markers;
- a finite test target capable of returning a requested exit code;
- a generic dependency Compose bundle with an endpoint owner plus optional helper, volume, config, secret, and internal network;
- a two-owner dependency bundle for multi-owner readiness cases;
- an intentionally unhealthy/delayed-health dependency;
- provider services with configurable endpoint names, schemes, ports, and publication intent;
- a tester Compose bundle with selected runner plus an unselected helper;
- invalid Dockerfiles/Compose files generated by mutation from known-valid fixtures.

Every negative fixture should differ from a valid control by the smallest possible change. This prevents a test from passing for the wrong validation reason.

## Assertion discipline

For every successful compile, inspect the normalized logical model and generated Compose. Assert semantic identity using configured service/dependency/endpoint paths; do **not** make tests depend on Builder-private generated names unless the test is specifically checking name isolation.

For every expected failure, assert:

1. non-zero/throwing result;
2. no partially runnable composition is emitted/executed when fail-fast behavior applies;
3. diagnostic contains enough source/logical context to locate the problem;
4. Builder did not silently apply a fallback.

For every runtime test, use bounded waits and explicit markers. Do not replace health-gating assertions with arbitrary sleeps.

## Conformance exit criteria

Treat Builder V2 as feature-complete only when:

- every scenario classified as schema/compiler behavior has an automated deterministic test;
- every health/network/resource behavior that cannot be proven from an AST/generated YAML has a Docker integration test;
- every supported public command has at least one CLI-level happy-path and relevant failure-path assertion;
- every documented legacy field has a rejection test;
- all positive fixtures compile without depending on Builder-private generated service/resource names;
- all negative fixtures fail for the intended reason before an incomplete runtime starts;
- repeated runs are deterministic subject only to the explicitly permitted AUTO-port availability/cache behavior;
- the entire 384-scenario matrix passes in CI on the supported Docker/Compose environment.

## Maintenance rule

When the V2 specification changes, update this suite **before or with** the implementation. Every new configuration field, stage behavior, endpoint property, lifecycle rule, publication mechanism, or exception must gain focused scenarios in exactly one primary catalog plus cross-feature regression coverage where interactions are material.
